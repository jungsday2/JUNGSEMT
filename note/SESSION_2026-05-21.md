## 1. 토론 — EMT_3bus의 초기 위상자 계산

### Q: 초기 위상자 계산은 뉴턴-랩슨인가 단순 옴의 법칙 반복인가?

**A: NR이 아니라 Picard fixed-point iteration**.

[simulator.py:114-148](EMT_3bus/simulator.py#L114-L148)의 `initialize()` 흐름:

```
Y 행렬 빌드 (1회, 파라미터에만 의존) — 절대 안 바뀜
loop (max_iter회):
    I_phasor 빌드 (능동 소자 상태에 의존, 매 반복 갱신)
    V_phasor_new = solve(Y, I_phasor)        # 선형 1-shot
    initialize_states(V_phasor_new)          # 회전자 backsolve
    수렴 체크: max|ΔV_phasor| < tol
```

| | NR (PF) | 우리 코드 |
|---|---|---|
| 방정식 | 비선형 PQ mismatch f(V)=0 | 선형 Y·V=I |
| 풀이 | J·ΔV = -f (야코비안) | V = Y⁻¹·I (Y 고정) |
| 부하 | PQ/PV 가능 | Constant-Z만 |
| 발전기 | PV 모선 처리 | PQ 모드 (T_m, Q_op 지정) |
| 반복 사유 | 비선형성 | 발전기 e''가 회전자 상태에 의존 |

### 핵심 통찰: 시차 굴림 (한 박자 늦은 Picard)

- **iter 0**: ψ''=δ=0 → I_gen=0 → 부하/슬랙만으로 V 1차 추정 → 그 V로 회전자 상태 *첫 계산*
- **iter 1**: iter 0의 회전자 상태로 I_gen 계산 → V 재추정 → 회전자 상태 갱신
- **iter ≥1**: |V_new − V_old| < tol 검사

핵심 메커니즘:
- `stamp_I_phasor`는 **"읽기"** (self.psi_d_pp 등 사용)
- `initialize_states`는 **"쓰기"** (self.psi_d_pp 등 갱신)
- 한 박자 늦은 갱신으로 self-consistent 해 찾음

### 왜 NR 안 써도 되나?

세 가지 단순화 덕분:
1. **Constant-Z 부하** (Y가 V-의존 안 함)
2. **발전기 PQ 모드** (T_m, Q_op 지정 — PV 모선 아님)
3. **Slack 강함** (R_int=0.001) → fixed-point contraction 빠름

비선형성은 **발전기 자기일관성 한 곳뿐** → picard로 5-10 iter면 수렴.

### t=0 시점 평가 (run() 정합)

[simulator.py:154-161](EMT_3bus/simulator.py#L154-L161):
- 컴포넌트 내부 이력 → **t = −Δt** 인스턴스
- 시뮬레이터의 `_V_nodes` → **t = 0** 인스턴스
- 두 시점이 정확히 Δt 떨어져야 trapezoidal 공식이 첫 스텝부터 깨끗하게 굴러감

```
V_history[:, 0] = 위상자 해의 t=0 평가값  ← bumpless의 정의
```

## 2. 토론 — NR로 초기화를 바꿔도 되나?

**결론**: 기술적으로 OK. 하지만 현재 코드 구조에선 ROI 낮음.

### 바꾸면 좋은 점
- Quadratic 수렴 (5-10 iter → 3-4 iter)
- PF의 표준 알고리즘 학습 가치

### 바꾸면 나쁜 점
1. picard도 이미 충분히 빠름 (slack-dominated 3-bus)
2. 컴포넌트 인터페이스에 `stamp_J_phasor` 추가 필요 → boilerplate 증가
3. NR은 초기값 민감 (V=0 출발 시 발산 가능 → flat start 필요)
4. 진짜 NR이 필요한 시점은 따로 있음 (Const-PQ 부하, PV 모선 도입 시)

### 권장 패턴

| 시점 | 방식 |
|---|---|
| 현재 (Const-Z + slack 강함) | picard 유지 |
| Const-PQ 부하 도입 | NR로 교체 (자연스러운 트리거) |
| PV 모선 / 멀티 머신 | NR 거의 필수 |

## 3. 토론 — ParaEMT는 Const-Z인데 왜 NR을 쓰나?

**핵심**: "Const-Z"는 EMT 단계의 동작 방식이고, NR은 그 직전 PF 단계의 도구.

ParaEMT는 [`main_step0_powerflow.py:60-69`](../ParaEMT_public-main/main_step0_powerflow.py#L60-L69)에서 PSS/E의 `fnsl` (Fast Newton-Raphson Solution)를 호출:

```python
psspy.fnsl([0, 0, 0, 1, 1, 0, 0, 0])   # full Newton-Raphson PF
```

### Const-Z여도 NR이 필요한 이유

1. **PF 입력 자체가 비선형**:
   - PV 모선 (|V| 지정, Q free)
   - PQ 부하
   - Slack, Q 제한, MW 스케줄
   → fixed-point picard로는 수렴 보장 X

2. **Const-Z는 PF 결과물**:
   ```
   [Step 0] NR PF (.raw → V_phasor, P_gen, Q_gen)
                 ↓
   [Step 1] Z_load = |V_PF|² / (P − jQ)*   ← 운전점에서 동결
                 ↓
   [Step 2] EMT 시뮬: 그 Z_load를 stamp
   ```

3. **실제 케이스 규모**: WECC 240-bus 등 다발전기 / 다 PV — picard 발산 가능

4. **Q 제한 enforcement**: PV → PQ 자동 전환 (NR이 자연스럽게 처리)

5. **신뢰성 요구**: NREL은 PSS/E의 30년 검증된 NR 솔버에 위임 (자체 reinvent 안 함). 차기 버전은 ANDES로 대체 예정 — **둘 다 NR 기반**.

### 우리 3-bus와의 결정적 차이

| | 우리 3-bus | ParaEMT |
|---|---|---|
| PF 단계 | EMT 시뮬레이터 내부 picard | 별도 단계 + 외부 PSS/E NR |
| 부하 입력 | Const-Z | PQ로 입력, PF 후 EMT용 Z로 변환 |
| 발전기 | T_m, Q_op (PQ 모드) | PV 모선 |
| Slack | R_int 있는 voltage source | 표준 slack |
| 규모 | 3 모선, slack-dominated | 9~240 모선, multi-machine |
| Bus type switching | 없음 | Q-limit hit → PV→PQ |

**핵심 발견**:
- ParaEMT는 **Full 8-winding GENROU** (Lf1d mutual, 0-seq 포함) — 우리 Simple GENROU와 차이
- **Schur reduction**으로 field+damper를 stator로 reduce → 매 스텝 inverse 2×2만
- **수치 댐핑 α=99/101** (~0.98) — 자동 적용 (우리는 옵션, 디폴트 0)
- **모든 hot-path JIT** — Numba `@njit(parallel=False)` 데코레이터, 내부 `prange` 사용
- **3점 외삽 가중치 `pd = 1.25·pv_1 + 0.5·pv_2 − 0.75·pv_3`** — 일반 quadratic이 아닌 ParaEMT 특제 (노이즈 감쇠와 외삽 균형)
- **`predictX → updateIg/Iibr → solveV → updateX/Xibr → updateIhis`** 한 스텝 루프
- **60 Hz hardcoded** in `numba_updateIibr:887` — 50 Hz 시스템 부정확 (버그)
- 코드 quirks 9개 정리 (dead code, gov_type 인덱싱 위험, REGCA HVPL 초기화 불일치 등)
